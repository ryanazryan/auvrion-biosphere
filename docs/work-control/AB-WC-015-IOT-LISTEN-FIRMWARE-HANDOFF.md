# Auvrion Biosphere — LISTEN IoT firmware handoff

Verified against `main` following PR #92 (26 Oct 2026). This is protocol documentation, **not a passed physical-device acceptance test**.

## Endpoint

`POST https://<deployed-host>/api/device/recordings` (local development: `http://localhost:3000` from the SAME computer). Device bearer credentials; do not send browser cookies or Origin header.

Required headers:

- `Authorization: Bearer abdev_v1_<43-char-base64url>` (generated from admin provisioning, never hardcode in public repository)
- `X-Device-ID: <UUID>`
- `X-Protocol-Version: 1`
- `X-Recording-ID: <unique stable ID per WAV, reused on retries>`
- `X-Observed-At: 2026-10-27T01:00:00Z` or omit header for unknown time
- `X-Clock-Quality: rtc_verified` or `unverified`
- `X-Ingestion-Mode: live` / `historical` / `simulation`
- `X-Audio-SHA256: <64 lowercase hex characters>`
- `X-Audio-Bytes: <exact binary length>`
- `X-Duration-Ms: <exact integer milliseconds>`
- `Content-Type: audio/wav`

HTTP body: **raw WAV bytes**, not JSON or multipart.

Format: RIFF/WAVE PCM signed 16-bit, mono or stereo, sample rate 16000, 44100 or 48000 Hz, max 30 seconds and max 10 MiB. Firmware should favor 16000 Hz / mono / 16-bit to minimize transmission size. Other constraints are checked by `src/server/evidence/wav-validation.ts`.

Success: HTTP 200 `{"protocolVersion":1,"status":"committed","receiptId":"...","deviceId":"...","recordingId":"...","observationId":"...","audioSha256":"...","audioBytes":123,"replayed":false}`.

On 503, timeout or lost connection: **keep the exact same recording ID and byte payload**, retry with bounded exponential backoff; do not claim successful delivery before a committed ACK. Same recording replay returns `replayed:true`. Different payload under same recording ID returns 409 conflict and must be investigated, not overwritten.

No device location is accepted in this ingestion protocol; observation location is marked unknown. No online heartbeat is available. A stored observation is not proof the device is currently online.

## Before connecting an ESP32

1. Provision an active LISTEN source and device in the Admin device workflow; capture the one-time token securely.
2. Confirm DB migrations through `0019` and private WAV storage `PRIVATE_EVIDENCE_DIR` exists.
3. Test the exact WAV generated by firmware against the validator, including duration and checksum.
4. Ensure HTTPS and hostname reachability from the ESP32 Wi-Fi network. `localhost` on ESP32 means the ESP32 itself, **not** the laptop.
5. Verify one normal ACK, one retry with `replayed:true`, a revoked-device 401, and private authorized playback. Do not rotate credentials during a test.
6. Verify SD buffering when Wi-Fi is absent, clock quality (DS3231 battery and UTC conversion), power integrity, and physical INMP441 I2S wiring.

## PREVENT limitation

The endpoint accepts LISTEN WAV only. **Do not POST BME280/PMS5003 telemetry as WAV or fabricate sensor readings.** PREVENT ingestion requires an independent authenticated measurement contract and implementation. Until then, environmental measurements are entered as explicitly identified manual or reference data.
